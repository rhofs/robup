# RobUp — Planning & Progress

_Last updated: 2026-08-12_

RobUp is a ClickUp-style task manager: Next.js 16 (App Router, Turbopack) + Prisma/SQLite + Zustand. Paused for a while in favor of Huly, now being actively picked back up.

**Status:** everything documented below is implemented and Playwright-verified against the local dev server. Several sessions' worth of work (Space/Folder/List drag-and-drop and reordering, undo/redo, Activity & Comments, the Calendar/Planner view, browser back/forward, the Docs tab, the Office tab and Cozy Rooms, Command palette, Docs drag-and-drop, and @-mentions) had been sitting uncommitted in the working tree the whole time — this is the single commit that finally captures all of it and pushes to `origin/main`. No merge was involved; `git log` has always been a plain sequential history.

## What's built and working

**Hierarchy:** Workspace > Space > Folder (nested, unlimited depth, optional) > List > Task > Subtask. A List can live directly under a Space with no folder. Spaces, Folders, and Lists all support a custom color + icon via right-click context menu ("Edit appearance" / "Rename" / "Delete" where applicable — Lists have no delete yet, see Next steps).

**Organizing the tree:**
- Drag-and-drop reparenting (drag a List/Folder onto another Folder to nest it, onto a Space header to un-nest it to that Space's top level) works **across Spaces**, not just within one — including moving a Folder with nested sub-folders/lists, which cascades their `spaceId` server-side.
- Drag-to-*reorder* siblings (drop a Folder on a sibling Folder, a List on a sibling List, or a Space header on another Space header) reorders them in place instead of nesting/doing nothing. Folder-onto-folder disambiguates by relationship: dropping on an existing sibling reorders; dropping on a folder elsewhere in the tree nests, same as before.
- Folder expand/collapse state persists across reloads (`localStorage`, key `robup.collapsedFolders`).
- Dropping a *task* onto a Space or Folder (rather than a specific List) auto-lands it in the one List found anywhere inside, recursively, if there's exactly one; if there's no List at all, a toast explains why instead of doing nothing silently; if there's more than one, a small picker (labeled with each List's folder path, e.g. "Ideer / Backend") lets you choose instead of guessing.

**Tasks (list view):**
- Sortable/resizable/reorderable columns (Name, Status, Assignee, dates, custom fields), persisted in `localStorage`.
- Custom fields, per-space statuses, assignees, archive/restore, bulk select + move/archive/delete.
- Task detail modal: subtasks table, named docs with autosave, comments/activity feed (collapsible, animated in/out), timeframe (start/due + time-of-day). Row-into-modal "magic move" expand animation.
- Sidebar: recursive Folder/List tree (`components/FolderTree.tsx`).

**Calendar view** (`components/calendar/`), labeled "Planner" in the nav rail:
- Month / Week / Day granularity, Gantt-style bars with lane assignment so a task keeps the same lane across week breaks — lane assignment and the visible-lane cap are computed **per connected overlap cluster**, not globally across the whole visible range, so a task that's no longer crowded reliably becomes visible again. Bar color follows the Space > Folder/List cascade (`taskColorOf` in `CalendarView.tsx` — a task's List color if set, else walking up its Folder chain, else the Space's color), not Status.
- Overflow past the visible-lane cap ("+N more") lives in its own reserved strip below the bars, not overlapping them, and is clickable to drill into that day.
- Day view lays out same-day timed events in side-by-side columns instead of stacking them on top of each other.
- Drag to reschedule: move (preserves duration) and resize-from-either-edge (works even on tasks that only have one of start/due set).
- Cross-week-row dragging via a live "ghost" preview. ISO week numbers, hover "+" quick-add per day, header "+ New task" button.
- Task creation is a required dialog (`components/CreateTaskModal.tsx`): Space and List must both be chosen explicitly — no "unsorted" fallback.
- **Calendar has its own sidebar mode**: multi-select filter (checkboxes, tri-state at any folder depth) instead of the Tasks tab's single-selection navigation. Same `FolderTree` component, different mode.
- **Personal `.ics` calendar feed**: each `User` has a `calendarToken` (opaque uuid, `GET /api/calendar/[token]` — public, no session needed, matching how every other external calendar subscription URL works). Feed is scoped to that person's assigned, non-archived tasks with a start/due date, as all-day events. The token is deliberately excluded from every other User-returning endpoint (team list, task assignees, comment authors — all `select` a `publicUserSelect` from `lib/prisma.ts` instead of `include: { assignees: true }`) and only ever handed out via `GET /api/users/[id]`, fetched on demand by the copy-link button (chain icon) next to the "You are: ..." selector.

**Multi-workspace** (sidebar header dropdown, `app/page.tsx`): switch between multiple `Workspace`s, each with its own membership (`Workspace.members`/`User.workspaces`) — a workspace with exactly one member is what "private" means in this app, no separate flag. Create new workspaces and add/remove members from the same dropdown. `GET /api/workspaces`/`GET /api/tasks`/`GET /api/task-docs` all filter by `?userId=` server-side, so a private workspace's content genuinely never reaches a non-member over the network (still not real auth — see the 2026-08-08 session below for the exact privacy bar). `Users` stay one global directory shared across every workspace. See that session entry for the full architecture, including the disclosed "You are: (none) now sees zero workspaces" behavior change.

**Navigation:** Huly-style narrow icon rail (Tasks / Planner / Docs / Office, plus Settings and Trash pinned at the bottom — each of the 4 view tabs individually hideable via the Settings menu, `activeView: 'board' | 'calendar' | 'docs' | 'office' | 'mytasks' | 'mypersonal' | 'profile'`) to the left of the sidebar. A persistent "Me" zone sits above the workspace switcher (avatar → profile page; "My tasks," a private cross-workspace quick-list; "My assigned tasks," scoped to the current workspace) — see the second 2026-08-08 session entry below. Clicking a Space with no List selected shows a dedicated **Space home page** (`components/SpaceHome.tsx`) instead of a flat task table: editable cover-image-URL banner + description (both inline click-to-edit, no modal), and a click-to-browse Folders/Lists card grid with breadcrumb drill-down. The old "flat table of every task in the Space" is gone entirely — union-of-tasks-across-lists is instead handled by **multi-select Lists** in the sidebar (Ctrl/Cmd-click to toggle a List in/out, Shift-click for a contiguous range in the same depth-first order the tree renders — `activeListIds: Set<string>` in the store, not a single value; scoped to one Space at a time, clicking into a different Space always starts a fresh single-selection there since a merged view can't sensibly show two Spaces' Statuses/CustomFields at once).

**Browser back/forward** works across the whole app — Space/List nav, the task-modal stack (including nested subtask modals), Planner's month/week/day drill-down and next/prev date, Docs-tab folder browsing/open-doc, and Office-tab person selection all round-trip through the URL query string on `/` (`lib/navUrl.ts` encode/decode, two `useEffect`s in `page.tsx` syncing state↔URL, each a no-op whenever the two already agree). Deep-linking works too (e.g. `/?space=...&modal=...`, `/?view=docs&space=...&doc=...`, or `/?view=office&officeUser=...` opens directly into that state), with graceful fallback to a safe default for stale/deleted ids.

**Docs** (third nav-rail tab): a standalone, folder-nested document system — `Space > DocFolder (nested) > Doc`, unified with the task modal's existing per-task Documents (same underlying `Doc` model; `taskId`/`spaceId`+`folderId` are independent, so a doc is task-scoped, Space/Folder-scoped, or **both at once**). Sidebar tree (`components/DocFolderTree.tsx`, drag-and-drop reorder/move/nest same as Folder/List — see below) and a breadcrumb card-grid browser (`components/DocsBrowser.tsx`, click-only, not a drop target, matching how `SpaceHome.tsx`'s grid isn't either) mirror the Folder/List tree's look (click-to-navigate, right-click-free — hover pencil/trash icons — "+ New folder"/"+ New doc" instead). Opening a doc shows a full-page editor (title input + `components/collab/CollabDocEditor.tsx`, live collaborative content — see "Real-time collaborative Doc editing" below) instead of a modal. Standalone docs don't participate in Activity & Comments (task-scoped concept, no task to log against).
A task's Documents panel can **link an existing standalone doc** onto the task ("Link existing" next to "+ New", scoped to standalone docs in the task's own Space) — the doc then shows up in both places at once. Linked docs get a small `Unlink` icon (next to Delete, on hover) to detach without destroying the doc; Delete stays a hard delete everywhere. The reverse also works: the standalone Doc editor (Docs tab) has its own "Link to task"/"Linked to: ..." control, scoped to Tasks in the doc's own Space. Both directions push through the same `setDocTaskLink` action and are Ctrl+Z-undoable.

**Doc export** (`components/collab/DocExportMenu.tsx`, next to the export-affected doc's title at both `CollabDocEditor` call sites): "Download PDF" (`GET /api/docs/[id]/export/pdf`, `pdfkit`) and "Export to Google Docs" (`POST /api/docs/[id]/export/google`, `googleapis` — needs a one-time per-person OAuth connect via a status control in the identity strip). Both read `Doc.ydoc` through a shared loader (`lib/collab/loadDocForExport.ts`), not the plain-text mirror, so bold/italic/headings/lists all survive. See the third 2026-08-07 session entry below for the full architecture, including the required Google Cloud setup step.

**Real-time collaborative Doc editing** ("like Google Docs" — multiple people typing in the same Doc at once, seeing each other's changes and cursors live): both Doc editors (task-modal Documents panel and the standalone Docs-tab editor) are now the same `components/collab/CollabDocEditor.tsx` (Tiptap + Yjs), replacing the old duplicated autosave-`<textarea>`+Notion-toggle blocks entirely. A separate sidecar Node process (`server/collabServer.ts`, `@hocuspocus/server`, run via `npm run dev:collab`/bundled into `npm run dev` via `concurrently` — port 1234, `COLLAB_PORT` env override) handles the live WebSocket sync, deliberately kept out of the Next server itself (`next dev`/`next start` stay untouched) to keep this app's "Zero-Cloud SQLite, one process" design change as small as possible — it's now two processes, but neither is a hosted/cloud dependency. `Doc.ydoc` (new `Bytes?` column) stores the binary Yjs snapshot; `Doc.content` (the pre-existing plain-text field) is kept as a synced mirror on every persist (`lib/collab/docJSONToPlainText.ts`) so `DocsBrowser.tsx`'s content preview keeps working unmodified — `PATCH /api/docs/[id]` no longer accepts `content` at all once this exists, closing off the old direct-write path so it can't race the sidecar's own writes. Existing plain-text docs (including any containing `@[Label](kind:id)` mention tokens) migrate lazily and exactly once, server-side inside `onLoadDocument` (`lib/collab/legacyContentToDocJSON.ts`, one `\n`-separated line → one paragraph node), the first time they're ever opened collaboratively — Hocuspocus coalesces concurrent first-loads of the same doc internally, so this can't double-run even if two people open a never-yet-converted doc at the same instant. Mentions are a custom Tiptap node (`lib/collab/mentionNode.ts`, shared by server schema + client) rendered as a live-resolving chip (`components/collab/MentionChip.tsx`, same pill styling as the plain-text `MentionText.tsx`) with its own `@`-autocomplete (`components/collab/mentionSuggestion.ts`, reusing `scoreMatch`/`resolveMentionEntity`) — this is Docs-only; Comments still use the original plain-text `MentionText`/`MentionTextarea` unchanged. Presence (`components/collab/PresenceBar.tsx` + Tiptap's `CollaborationCaret` for in-text cursors) is sourced from the same "You are: ..." self-selected identity (`useSessionStore`) every other attribution in the app already uses, with each person's existing `User.color`. Ctrl+Z inside the editor is handled by Yjs's own `Y.UndoManager` (via the `Collaboration` extension's built-in keymap) rather than the app's global history stack — verified this correctly reverts only your own last edit even when someone else's concurrent edit is interleaved with it, which a snapshot-diff undo model fundamentally can't do; the app's global Ctrl+Z listener already no-ops whenever focus is inside a `contenteditable`, so no changes were needed there. Formatting: Bold, Italic, Underline, Strikethrough, Heading (levels 1–2), Bullet list, Ordered list, text alignment, font family/size, text/highlight color, and links, via a collapsible side panel (`components/collab/DocFormatPanel.tsx`, moved from an earlier fixed toolbar row — see the 2026-08-11 "Round 4" session below) — initially shipped deliberately minimal (paragraphs + mentions only, same ceiling as the old textarea) on 2026-08-07, extended same-day to Bold/Italic/Heading/lists, then extended again 2026-08-11 to the full set above (see that session's own entry for the export-path details).

**Office** (fourth nav-rail tab, `components/OfficePage.tsx`): a Huly-style team directory, not a settings page. Sidebar shows a flat list of team members (no Space/Folder concept for people); once you pick someone, their own page: avatar, inline click-to-edit phone/title/status (`User.phone`/`title`/`status`), and every task assigned to them across every Space, with a Space/List breadcrumb per task since they're no longer confined to one. Status colors there fall back to `DEFAULT_STATUSES` rather than any one Space's custom palette — the same simplification the Calendar view already makes for cross-Space task lists. Three ways back from a person's page: the "← Back to team" link, the clickable "Office" breadcrumb segment, or clicking the Office nav-rail icon again (which always resets, even when Office is already the active tab).

**Office rooms — the "HQ Building"** (`components/OfficeRooms.tsx`, the tab's default view): a gamified base-building floor plan, replacing an earlier flat card-grid version. A message-of-the-day banner (`Workspace.messageOfTheDay`, warm amber accent, deliberately breaking from the app's usual neutral chrome) sits above a stacked building: `Room`s render as full-width connected "floors" (`FloorRoom`, sorted by descending `order` so the newest/highest-`order` room renders at the top — `POST /api/rooms` computes `(current max order) + 1` at creation time specifically so new floors land there, not tied at the schema default), and a `Lobby` (renamed from the old "Unassigned" tray, same amber accent as the banner) anchored at the bottom for team members not in any room. Team members drag between the Lobby and any floor; overlapping "collaborating" avatar clusters (negative-margin overlap + a separation ring, `PersonAvatar`/`DraggableAvatar`) replace the old individual name-pill chips. Reuses the app's single shared `DndContext` (`app/page.tsx`) via id prefixes (`person-drag:`/`room-drop:`/`room-drag:`) dispatched in the existing `handleTaskDragEnd`, rather than a second nested context — the codebase has a documented gotcha about exactly that mistake. Rooms are also drag-reorderable among themselves (reuses the same `room-drop:` droppable, disambiguated by the dragged id's prefix; the drag handle is scoped to just the floor's header row so it doesn't shadow each avatar's own independent drag underneath).

**Do Not Disturb**, at both levels: a person can be individually DND (a small clickable status-dot badge directly on their avatar — works everywhere that avatar renders — red ring + dot when active, `User.isDnd`), and a room can *independently* be marked DND too (a door-icon toggle on the floor header, e.g. "meeting in progress" even if members aren't personally DND, `Room.isDnd`). Both are plain booleans through the existing generic `updateRoom`/`updateUser` patch actions, no new store actions.

**Live presence** ("who's online right now"): a small green dot on every avatar (`components/PersonAvatar.tsx`, opposite corner from the DND dot so the two never collide), driven by genuine real-time connection detection — not a manual toggle. Reuses the existing unauthenticated "You are: ..." identity and the existing Hocuspocus collaboration sidecar (a dedicated presence-only room, `lib/collab/usePresenceConnection.ts` + `store/usePresenceStore.ts`) rather than building real login/session infrastructure, which this app still doesn't have. See the second 2026-08-07 session entry below.

**Room detail — "step inside"** (`components/RoomDetail.tsx`, reached via a floor's expand button, or a person page's "Back to team" always clears both selections so you never get stranded): editable name, a big labeled DND switch, and — moved here entirely from the old floor-header popover — the icon/color decorate controls (`ROOM_ICON_CHOICES`/`ROOM_COLOR_CHOICES`), plus a browse-only member list (bigger avatars, click through to a person's own page). `OfficePage.tsx` is now a three-way branch (`activeUserId` → person page, else `activeRoomId` → `RoomDetail`, else the HQ Building), backed by a new `activeOfficeRoomId`/`setActiveOfficeRoomId` in the store and a matching `officeRoomId` URL-sync field mirroring the existing `officeUserId` handling.

Deleting a Room still un-assigns its members (`onDelete: SetNull` on `User.roomId`) rather than deleting people; undo restores both the room and everyone's assignment. Each floor shows a live task count (assigned tasks across its members). Person chips' inline self-authored `status` text and a `title` (role/tagline) field on their own page are unchanged from before.

**Command palette** (`components/CommandPalette.tsx`) — `Ctrl+K`/`Cmd+K` anywhere in the app (deliberately *not* skipped while focus is in a text field, unlike the undo/redo shortcut — same "opens from anywhere" behavior as Linear/Notion/Slack), or the "Search..." affordance at the top of the sidebar. Searches Task titles, **every** Doc title (both standalone Docs-tab docs and task-scoped ones — the latter bulk-loaded via `GET /api/task-docs` into the store's `docs` record at startup, no longer only per-task on modal-open), People names, and Space/List names — all loaded eagerly client-side, case-insensitive substring match, scored (exact > starts-with > substring), capped per category, ↑/↓/Enter/Escape keyboard nav. Jumping reuses existing setters entirely (`setModalTaskStack`/`setNavigation`/`setDocsNavigation`/`setActiveOfficeUserId`) — no new navigation logic; a task-scoped doc result opens its owning task (no deep-link to the specific doc tab within the modal).

**@-mentions**: type `@` in the task comment box or a Doc (task-modal or Docs-tab) to autocomplete a Task, standalone Doc, or User, same scoring/data source as the Command palette. Stored as plain text (`@[Label](kind:id)`, `lib/mentions.ts`) inside the existing `Comment.body`/`Doc.content` fields — no schema change. Renders as a clickable chip (`components/MentionText.tsx`) that live-resolves the mentioned entity's current name and jumps to it; a deleted entity falls back to a muted, non-clickable chip instead of breaking. The Doc editor (which has no separate read/write mode otherwise) gained a Notion-style view/edit toggle so its mentions can render as chips: rendered view when not focused, the raw `<textarea>` (`components/MentionTextarea.tsx`) on click.

Spaces, Folders, and Lists can all be **created and deleted** from the sidebar (`+` button / right-click menu + confirm dialog), not just renamed — cascades to everything nested, all restorable via undo (see below).

**Undo/redo — Ctrl+Z / Ctrl+Shift+Z** covers essentially every mutation: field edits, moves, reorders, creates, and deletes (including deletes that cascade through an entire Space→Folder→List→Task→Comment/Doc subtree, restored with the exact original ids so nothing else needs to change). Architecture: `store/useHistoryStore.ts` is a generic undo/redo stack + `transaction()` (groups N store calls from one bulk action/drag-reorder into a single undo step) + `pushCoalesced()` (merges a burst of same-key pushes — e.g. one doc-content edit session's autosave ticks — into one step instead of one per keystroke). Every mutating action in `useTaskStore.ts` captures its old value before writing and pushes `{undo: () => sameAction(...old), redo: () => sameAction(...new)}` — no separate inverse-logic to maintain. Cascading-delete undo restores a JSON snapshot (captured before delete) by replaying the same create/update actions with explicit ids (every POST route accepts an optional `id`), then a couple of safety-net refetches. **Exception**: a Doc's *content* (not its title) is no longer part of this stack — see "Real-time collaborative Doc editing" below, where Ctrl+Z inside the collaborative editor is handled by Yjs's own per-client undo instead, since a snapshot-diff model can't express "undo my last edit" correctly once someone else's concurrent edits are interleaved with it.

**Activity & Comments** (task modal, right panel) now logs real activity, not just the four original field-change types: task creation, title changes, assignee changes, Doc create/rename/edit-session/delete (one entry per edit *session*, bounded by focus→blur, not per autosave tick), and subtask add/remove — logged **one level only** on the immediate parent, never bubbling further up if that subtask itself gets a subtask. Every entry is attributed via the Comment model's existing (until now unused) `authorId` relation to whoever is picked in a new **"You are: ..." selector** at the bottom of the sidebar (`store/useSessionStore.ts`, localStorage-persisted) — a deliberate stand-in for real auth, isolated in its own store so swapping in real login later only touches that one file. Activity rows render a real Lucide icon per `Comment.activityKind` (schema field) instead of emoji, matching the rest of the app's icon language; entries logged before this existed just fall back to the old plain-dot marker.

**Visual design:** Matches Huly's look — neutral gray (`neutral-*`, not `slate-*`, which has a blue undertone) for chrome, blue reserved for buttons/selected state, sharp-ish corners, custom thin scrollbars, muted/pastel accent palette (`FIELD_COLOR_CHOICES` in `page.tsx`) for statuses/Space/Folder/List colors and user avatars.

## Today's session (2026-07-30)

**Part 1 — Gantt bars silently vanishing on crowded days** (user report: bars disappear past 4 overlapping and don't come back). Two real, separate bugs found and fixed (committed `73d83b4`):
- The "+N more" overflow indicator was rendered inside the day-number badge's own zone — the exact spot where visible bars start — so on the busiest days (the ones that most needed the indicator) it was painted over and invisible. Fixed by giving it its own reserved strip (`overflowTop` in `CalendarView.tsx`, rendered in `WeekRow.tsx`) with explicit `z-10` (needed because the day-cell's full-height button was otherwise intercepting clicks despite later DOM order — root cause not fully explained, pragmatically fixed).
- **Day view** had no lane/collision logic at all for same-day timed events — they rendered `absolute left-0 right-0` directly on top of each other, so only the last one in paint order was ever visible, no indication anything else was there. Fixed with a new `layoutDayColumns` helper (`lib/ganttLayout.ts`) that splits same-day overlapping events into side-by-side columns, grouped per connected overlap cluster.
- While re-verifying, the user found a third, deeper issue: freeing up space on a crowded day didn't reduce its "+N more" count or bring a hidden task back. Root cause: `assignLanes`'s lane numbering and cap-compaction ran **globally** across the whole visible month, so a task with real breathing room on its own day could stay stuck past the cap just because some unrelated pileup elsewhere in the month still occupied the low lane numbers. Fixed by scoping both lane assignment and compaction to each connected overlap cluster instead of the whole range. (Introduced-then-caught a same-day edge case in the process: the cluster-merge boundary used strict `<` instead of `<=`, which wrongly treated two tasks with an identical single-day range as non-overlapping.)

**Part 2 — five "smaller polish" items from the previous session's Next steps list**, all done and Playwright-verified:
1. Raised `MONTH_MAX_LANES`/`WEEK_MAX_LANES` (4→6, 8→12) now that bars are thinner, so more overlap is visible before "+N more" kicks in.
2. Folder expand/collapse now persists (`localStorage`).
3. Folder context menu gained Rename + Delete (previously only "Edit appearance").
4. Dropping a task onto a Folder row now lands it in the first List found recursively inside, instead of doing nothing.
5. Drag-to-reorder among Folder/List siblings, using a new `order` field already on both models — see "Organizing the tree" above for the reorder-vs-nest disambiguation rule.

**Part 3 — four more requests from continued use**, all done and Playwright-verified:
1. **Cross-Space drag-and-drop.** Previously, moving a List/Folder into a different Space's Folder or onto its header silently did nothing — the code only ever looked up the drop target inside the *source* Space. Fixed by searching all Spaces for the target, and by teaching the API (`/api/folders/[id]`, `/api/lists/[id]`) to accept a `spaceId` change; moving a Folder now cascades the new `spaceId` down through every nested sub-folder and List server-side. Cross-Space moves resync via a new lightweight `refetchWorkspaces` store action instead of trying to hand-patch two Space objects' arrays in place.
2. **List context menu** (Rename + Edit appearance), mirroring Folder's. `List` gained nullable `color`/`icon` columns.
3. **Space reordering**, same drag-to-reorder pattern as Folder/List, using a new `order` field on `Space`. Space headers are now both draggable (`space-drag:${id}`) and droppable (`space:${id}`, reused from the existing task-drop/cross-Space-move target — same "reuse the existing droppable, dispatch on the dragged id's prefix" trick used for List reordering, to avoid a second droppable colliding on the same rect).
4. **Toast on invalid task drop.** Dropping a task onto a Space or Folder with no List anywhere inside it (recursively) now shows a bottom-of-screen message explaining why, instead of silently doing nothing. First minimal toast system in the app (`toast` state + `showToast()` in `page.tsx`, no library).

All of today's work verified in a real browser via Playwright against the dev server, not just eyeballed — including cascading `spaceId` updates checked via direct `/api/workspaces` fetches, not just optimistic UI state.

Schema changes today: `List.color`, `List.icon`, `Space.order` (all via `prisma db push`, no migrations dir in this project).

## Today's session (2026-07-31)

Long session, five features end to end, each Playwright-verified against the dev server with server-side data checks (not just optimistic UI):

1. **Space home page** — replaced the old "clicking a Space shows a flat table of everything inside it" with a dedicated home page (cover/description/Folders-Lists browser). "See all tasks across a Space" was deliberately *not* rebuilt here — moved to multi-select instead (below).
2. **Space create/delete**, plus **`deleteList`** (previously missing entirely) and a fix for the known "Space reordering has no landing-spot feedback" friction — a live insertion-line indicator during drag. Along the way, discovered a Space's *own* drop target only covers its header row, not its whole expanded height when it has folders/lists open — dragging past a "tall" Space now correctly treats hovering anywhere in its own tree as "below this Space," not just its header.
3. **Full undo/redo** (Ctrl+Z / Ctrl+Shift+Z) — see "What's built" above for the architecture. Two real bugs surfaced only under actual runtime testing, not code review: (a) a race where the undo entry for a delete became available *before* the DELETE request had actually completed, so a fast Ctrl+Z could try to recreate a row the server hadn't removed yet → unique-constraint error; fixed by deferring the history push until after the delete's fetch resolves. (b) the keystroke-coalescing helper (`pushCoalesced`) was overwriting the *whole* stored undo entry on every call instead of keeping the first call's `undo` and only advancing `redo` — meant Ctrl+Z on a doc edit only reverted the last keystroke, not the session.
4. **Activity & Comments overhaul** — attribution (new "You are" selector), task-creation/title-change/doc/subtask logging, real icons instead of emoji (new `Comment.activityKind` column). The trickiest part wasn't the logging itself but *not* double-logging: restoring a deleted task via undo replays its original activity comments verbatim from the snapshot, so the same field-setting calls used to reconstruct it (set assignees, archive, etc.) needed a way to know "this is a mechanical replay, don't also generate a fresh log entry" — a module-level `isRestoringSnapshot` flag in `useTaskStore.ts`, set only for the duration of a snapshot-restore call, threaded into the relevant PATCH bodies as `skipActivityLog`.
5. **Multi-select Lists** in the Tasks-tab sidebar (Ctrl/Cmd toggle, Shift range-select) — `activeListId: string | null` → `activeListIds: Set<string>` throughout the store/page/FolderTree. New `getOrderedListIds` helper in `lib/folderTree.ts` mirrors the sidebar's actual depth-first render order so a Shift-click range "looks right" even across a currently-collapsed folder.

Schema changes today: `Comment.activityKind` (all via `prisma db push`, no migrations dir in this project — remember to stop the dev server first, see Known bugs).

## Today's session (2026-08-10, continued) — Login completely dead when reached from a second machine on the LAN

User report: testing from a second physical computer ("PC 2") against the dev server running on "PC 1," none of the login page's buttons did anything at all. Traced to the dev server's own logs, which had already recorded the exact cause of both underlying problems the moment PC 2 tried:

1. **`⚠ Blocked cross-origin request to Next.js dev resource /_next/webpack-hmr from "192.168.1.51"`** — Next's dev server blocks cross-origin requests to dev-only resources (the Turbopack/HMR websocket) by default; reaching the dev server via its own printed "Network: http://192.168.1.51:3000" LAN address (instead of `localhost`) trips this, which can leave the page half-hydrated — indistinguishable from "the buttons don't work," since no click handlers ever actually attach. ## Today's session (2026-08-10, continued) — Google OAuth from a second machine: nip.io + AUTH_URL

## Known bugs / things to remember

- **dnd-kit gotcha**: `useDraggable`/`useDroppable` bind to the *nearest ancestor* `DndContext` by React-tree position, not by id-naming intent. Fix: one shared `DndContext` for all sidebar/task dragging, dispatch in `onDragEnd` by inspecting the dragged id's prefix (`task id`, `list-drag:`, `folder-drag:`, `space-drag:`).
- **A second droppable on the exact same DOM rect ties in collision detection** — dnd-kit's `closestCenter` can't meaningfully prefer one over the other when their centers are identical, so the "winner" is effectively arbitrary. Hit this twice: once (correctly avoided) by reusing List's existing `list:` task-drop target for List-reorder instead of adding a second droppable there; and initially got it wrong for Space reordering in the same way before applying the same fix. When something is draggable AND needs a reorder-drop-target at the same location, reuse an existing droppable id and disambiguate by the *dragged* id's prefix instead of registering a second `useDroppable` there.
- **Interval/cluster boundary math needs `<=`, not `<`, for single-point-in-time ranges.** A same-day task has `start === end`; a merge-overlapping-intervals boundary check using strict `<` will treat two such tasks as non-overlapping neighbors instead of a real conflict. Hit this in `assignLanes` (calendar lanes) — watch for it again if any other interval-clustering code gets added.
- **Async store actions in drag-end handlers are fire-and-forget.** `reorderSpace`/`reorderList`/`updateFolder` etc. return promises but callers don't await them — fine for the app itself (optimistic local state updates synchronously), but when verifying via a direct API fetch right after a script-driven drag, give the network request a moment (a few hundred ms to ~1s) before checking, or the check can race ahead of the PATCH actually landing and look like a failure that isn't one.
- **Framer Motion `layoutId` gotcha**: matches globally by default (no `LayoutGroup` in this app) — scope the id string to whatever makes two instances *actually* the same logical element (see `TaskRow`'s `navScope` prop).
- **Playwright drag scripts: grab the source element at its own center, not an arbitrary offset like "5px from the left edge."** dnd-kit's collision detection tracks the *dragged element's* translated rect (original rect shifted by however far the pointer has moved from its mouse-down point), not the raw cursor position. Grabbing off-center means the effective drop point is offset from where the mouse visually ends up — with tightly-packed sidebar rows (e.g. a folder immediately followed by its own nested child), that offset is enough to land the drop one row off from the intended target. Cost an hour of confused debugging (looked like a real move-into-child-folder bug) during Docs drag-and-drop verification before realizing it was the test script's grab point, not the app.
- Tailwind's `slate-*` palette has a real blue undertone — use `neutral-*` for "neutral gray."
- This machine reliably needs a dev-server restart after any `prisma db push`/schema change: `prisma generate` fails with `EPERM` on the query-engine DLL while the dev server holds it open. - **dnd-kit's `onDragOver` only fires when the closest droppable *changes*, not on every pointer move.** Learned this building the Space drag-reorder insertion indicator: comparing the dragged element's rect to the target's rect *inside* the `onDragOver` callback gives a stale, essentially arbitrary snapshot near a boundary, since the callback simply doesn't re-fire while the pointer moves within the same closest-droppable's territory. Fix: track *which* droppable is closest via `onDragOver` (event-driven), but compute fine-grained "where within it" continuously from a raw `window.addEventListener('pointermove', ...)` instead.
- **Undo/redo: push the history entry only *after* the mutating fetch has actually resolved, not before.** Pushing first (so it "feels" symmetric with the code order) creates a real race: a fast Ctrl+Z can fire the inverse action before the original write has committed server-side — hit this exactly with delete+undo, where undo's re-create raced an in-flight DELETE and got a unique-constraint error because the row it was "restoring" hadn't actually been removed yet.
- **A "coalesce a burst of calls into one undo step" helper must keep the *first* call's `undo` and only ever advance `redo`.** Overwriting the whole stored entry on each call (as a first draft of `pushCoalesced` did) means Ctrl+Z only reverts the most recent call in the burst, not the whole session — silently defeats the entire point of coalescing.
- **A new required column with a `@default` on an existing table can't go straight to required via `prisma db push`** — SQLite has no way to backfill existing rows with a *client-side* Prisma default in one step, so `db push` refuses. Two-step it: add the column as optional (`String?`, still `@unique` if needed) and push, backfill existing rows with a script, then flip it to required with the real `@default(...)` and push again. Hit this adding `User.calendarToken`.
- **Any nested `include: { someRelation: true }` on a model that carries a secret-ish field ships that field to every caller of the outer route, not just the ones that "should" see it.** Adding `User.calendarToken` (a bearer secret for the `.ics` feed) immediately leaked through `Task.assignees` and `Comment.author` on routes that had `include: { assignees: true }` / `include: { author: true }` — neither of those routes has anything to do with calendar feeds, they just happened to embed a `User`. Fix: a shared `publicUserSelect` (`lib/prisma.ts`) used everywhere a `User` is nested inside another model's response; only `GET /api/users/[id]` returns the real thing. Worth grepping for `include: { <relation>: true }` on any model any time a new sensitive field gets added to it.
- **Restoring a deleted entity from a snapshot needs a way to tell its own field-setters "don't log this as a fresh event."** The snapshot already contains the original activity-log comments, replayed verbatim — if the same `optimisticArchiveTask`/`optimisticSetAssignees`-style calls used to reconstruct the entity *also* trigger their normal "log this change" side effect, you get duplicates. Solved with a module-level `isRestoringSnapshot` flag in `useTaskStore.ts`, true only for the duration of a snapshot-restore call, threaded into the relevant request bodies as `skipActivityLog`.
- **A two-way state<->URL sync effect pair only needs a mutual "already equal, so no-op" check on both sides — not a manual reentrancy flag.** But two adjacent gotchas bit this in `page.tsx`'s back/forward sync: (1) don't special-case "the first push after hydration" as a `router.replace` meant to silently normalize a messy URL — that effect only runs when something *changes*, so "first push" is in practice almost always the user's first real click, and demoting it to `replace` collapses two navigations into one back-step. Just always `push` once hydrated. (2) a bare URL segment meaning "no opinion, don't touch" is only correct on the very *first* hydration pass (so a fresh `/` keeps an app default like auto-selecting the first Space) — on every later parse (a real back-navigation landing on that same bare URL), it must resolve to the concrete default instead, or backing past the user's first-ever choice does nothing visible.
- **Optional chaining (`a?.b.c()`) only protects against `a` itself being nullish — it does nothing if `a` is real but `.b` is `undefined` for some other reason (like a field-name mismatch between an API response and its TypeScript type).** `currentSpace?.spaceDocs.find(...)` crashed on every render once `currentSpace` became a real object, because the actual JSON field was named `docs` (matching the Prisma relation), not `spaceDocs` (the frontend type). TypeScript didn't catch it either, since the API response is untyped JSON at the fetch boundary. When a `select`/`include` field name and a frontend type's field name need to differ (to avoid colliding with another field, as here), rename explicitly in the API route's response mapping — don't rely on chained optional-access to paper over the mismatch, and don't assume TS will catch a field that only ever flows through an untyped `fetch().json()`.
- **Don't couple "navigate into X" with "toggle X's expand/collapse" in one click handler.** `DocFolderRow`'s row click did both — clicking an already-expanded folder to browse into it also collapsed it, so its own "+ New doc" row (rendered only while expanded) vanished out from under a click that was about to use it. The chevron already has its own dedicated toggle with `stopPropagation`; the row's own click should always *navigate and expand*, never toggle closed.
- **A "fix every leak" pass on a sensitive field needs to check a route's own un-`select`ed return value, not just its `include`s of other models.** The `calendarToken` leak fix earlier this session only grepped for `include: { <relation>: true }` (the `Task.assignees`/`Comment.author` case) — it missed that `POST /api/users` and `PATCH /api/users/[id]` *return the row they just wrote*, `prisma.user.create()`/`.update()` with no `select`, which is the exact same class of leak but doesn't match an `include` grep at all. When auditing a model for a newly-added sensitive field, check every `create`/`update`/`upsert` on that model too, not just places it's nested inside something else.
- **An optimistic mutation that removes/changes local state before the fetch resolves needs to check the response and roll back on failure — "fire and forget" silently loses data.** Every delete action in `useTaskStore.ts` updated state first, then `await fetch(...)` with no `.ok` check and no catch; if the request failed (dropped connection, dev-server restart mid-request — a real risk on this machine, see the `db push`/EPERM entry above), the item stayed hidden in the UI forever with no server-side effect and no trash entry, and nothing told the user anything had gone wrong. Fixed across all seven delete actions: check `res.ok`/catch the rejected promise, and on failure resync from the server (`refetchWorkspaces`/`refetchTasks`/`fetchDocs`) plus an `alert()` so it's never silent. Worth the same check any time an optimistic update's own confirmation request is added.
- **Playwright auto-dismisses native `window.confirm()`/`window.alert()` dialogs unless a `page.on('dialog', ...)` handler is registered.** Cost real debugging time verifying task delete: the click on "Delete" appeared to succeed (no thrown error) but the task was never actually removed, because `handleDeleteTask`'s `window.confirm(...)` guard was silently getting auto-cancelled. Not an app bug — the app already correctly uses a native confirm here (unlike the `ConfirmDialog` component used for space/list/folder/trash-purge deletes). Any Playwright script driving a flow that hits `window.confirm`/`alert`/`prompt` needs the dialog handler wired up first, or the action underneath it never happens.
- **`transaction(label, fn)` only groups pushes that happen synchronously (or before an awaited `fn` resolves) — a plain `.forEach` calling an un-awaited async action doesn't qualify, even though it *looks* like it's "inside" the transaction.** `transaction()`'s `finish()` runs the instant `fn()` returns; if `fn` is a sync function whose body fires off async calls without awaiting them (e.g. `arrayMove(...).forEach((x, i) => updateThing(x.id, {order: i}))`), the group closes and (if empty) gets discarded before any of those calls' own `push()` — which for most `updateX` actions in `useTaskStore.ts` only happens *after* their own `await fetch(...)` resolves — has landed. Each update then pushes its own entry directly onto the bare stack instead of being bundled, so Ctrl+Z only reverts whichever one happened to push last. Silent and easy to miss: a 2-item swap often only changes one side's `order` in practice (the other's old value already equals its new index), so only one update fires and there's nothing to split apart — this hid the bug through every single/double-item reorder test done earlier in the project. Only surfaced once a 3-way tie forced a genuine 2-item simultaneous change during the Office Rooms reorder work. Fix: make `fn` itself `async` and `Promise.all` (or sequentially `await`) every update inside it — `transaction()` already special-cases a `Promise`-returning `fn` and waits for it before closing the group. Applies to every `reorder*Siblings`-shaped helper; doesn't apply to actions (like `optimisticArchiveTask`) whose `push()` happens synchronously before the fetch is even awaited.
- **Creating a resource with a real side effect (opening a WebSocket, starting a timer, subscribing to something) inside `useMemo` is unsafe — React's dev-mode Strict Mode double-invokes `useMemo` factories specifically to catch this, and only "keeps" one of the two results, silently orphaning whatever the other one created.** `components/collab/CollabDocEditor.tsx` built its `HocuspocusProvider` (whose constructor opens a live WebSocket) inside `useMemo(() => new HocuspocusProvider(...), [docId])` — two real connections opened, React kept one, and typed edits went into whichever Y.Doc ended up bound to the *discarded* connection roughly as often as the kept one, so they silently never reached the server. On-screen everything looked correct (the character appeared as typed); only a reload or a second client revealed nothing had actually synced. Fix: move any side-effecting resource's create/destroy into `useEffect` + `useState` (create on mount, destroy in the cleanup, recreate when deps change) — the correct Strict-Mode-safe lifecycle — and reserve `useMemo` for genuinely pure derived values, per React's own stated contract for the hook.
- **Hocuspocus's `unloadImmediately` defaults to `true`: a document unloads from server memory the instant its last client disconnects, even if a debounced `onStoreDocument` write is still pending.** Closing a tab shortly after typing (comfortably inside the configured `debounce` window) silently lost that edit — the pending write never got the chance to run, and the next `onLoadDocument` re-read the old, pre-edit row from the database with no error anywhere. Set `unloadImmediately: false` (`server/collabServer.ts`) so the server waits out the pending debounced store before actually unloading; `flushPendingStores()` is the equivalent explicit escape hatch for a clean server-shutdown path if one gets built later.
- **A "sort by `order`" view can't tell a freshly created row apart from an old untouched one if the create route never actually sets `order`** — it just inherits the schema's `@default(0)` and ties with everything else that's never been manually reordered. `POST /api/rooms` was exactly this: the new HQ Building view sorts floors by descending `order` to put the newest on top, but new rooms silently landed at the bottom because they tied at 0 with existing rooms and a stable sort preserves creation-order for ties. Any "append at the end/top" UI built on an `order` field needs the creation route to actually compute `(current max) + 1` — don't assume a field exists just because the type does.
- **A positional Playwright locator (`.first()`/`.last()`) is unsafe for a *destructive* click while the exact ordering it's relying on is still being fixed in the same session.** Verifying the fix above, an early test script clicked "the newest room's delete button" via `.first()` — written before the ordering bug was actually fixed, so at that moment the newest test room was tied with a real pre-existing room ("Robs kontor") and, thanks to sort stability, the *real* room rendered first and got deleted instead. Caught by cross-checking the database, not by trusting the screenshot. Once list order itself is what's under test, scope destructive actions to an element matched by name/id, never by position.
- **`components/collab/PresenceBar.tsx` renders as a sibling of `.collab-doc-editor` in `CollabDocEditor.tsx`'s JSX, not inside it.** A verification script querying `.collab-doc-editor`'s own `innerHTML` for a peer's name will always come back empty, even when presence is working correctly — query the shared parent instead. Cost a chunk of debugging time chasing a phantom "presence broken" regression (even disabling the change under test didn't fix it) before realizing the test's DOM scope, not the app, was wrong.
- **A component that only reads its "who am I" identity once at construction time won't pick up a later identity switch without remounting.** `CollabDocEditor.tsx`'s `useEditor` dependency array is `[docId, provider]` — it deliberately doesn't include the current user, so `CollaborationCaret`'s displayed name is fixed at whatever "You are: ..." was set to when the editor first mounted; switching identity after a doc is already open doesn't retroactively relabel that tab's cursor until the doc is reopened. Predates this session, not a regression from anything built here — but worth knowing before writing a test (or filing a bug) that selects identity *after* opening a doc and expects the collaboration caret to reflect it.
- **A package that loads its own asset files (fonts, binaries, data) via `__dirname`-relative paths at runtime will break under Turbopack/webpack's default route-handler bundling, and the resulting error path is misleading.** `pdfkit` (added for Doc → PDF export) threw `ENOENT ... C:\ROOT\node_modules\pdfkit\js\data\Helvetica.afm` — a path that doesn't even resemble this project's real location (`C:\dev\robup\...`), because bundling rewrites/virtualizes `__dirname` inside the compiled route handler. Fixed with `serverExternalPackages: ["pdfkit"]` in `next.config.ts`, which tells Next to `require()` it natively from `node_modules` instead of bundling it — the same treatment Next's own defaults already give `sharp`/`better-sqlite3`/`canvas` for exactly this class of package (see the full auto-external list in `node_modules/next/dist/docs/.../serverExternalPackages.md` — checked directly rather than assumed, per this repo's own "not the Next.js you know, read the docs" instruction in AGENTS.md, since the option was renamed from `serverComponentsExternalPackages` in older Next versions). A `next.config.ts` change needs a dev-server restart to take effect — saving the file alone doesn't trigger Turbopack to pick it up.
- **A "find-or-create" route needs a real DB-level unique constraint plus an atomic `upsert`, not a `findFirst`-then-`create` pair — no amount of careful sequencing on the write side closes the gap between the read and the write.** `POST /api/workspaces/personal`'s first draft checked for an existing personal workspace, then created one if missing — two near-simultaneous requests (the sidebar's "My tasks" click called it, and `PersonalTasksPage.tsx`'s own mount effect called it again for deep-linking, then both doubled again by React Strict Mode's dev double-invoke) could each see "nothing exists yet" before either had committed, creating multiple personal workspaces for the same user. Fixed with a unique `Workspace.personalOwnerId` column and a single `prisma.workspace.upsert({ where: { personalOwnerId } })` — verified by firing 10 genuinely concurrent requests via `Promise.all` and confirming they all converged on one row. React Strict Mode's double-invocation is worth treating as a free, built-in race detector for exactly this class of bug during dev, not just an annoyance to work around.
- **When adding an auth check to a `[id]` route, grep the actual call sites before assuming "the caller can only act on their own id" is the intended rule.** Locking down `/api/users/[id]` PATCH/DELETE, a naive `callerId === id` check looked obviously correct — until grepping turned up the Office directory editing *other* teammates' phone/title/status/DND (`onUpdatePhone`/`onUpdateUserField`/`onToggleDnd`) and the Team panel's "remove a team member" both legitimately calling the same endpoints with someone *else's* id. A self-only check would have silently broken both real features while looking like a clean security fix. Landed on "must be authenticated, doesn't have to be the same id" instead — this app has no admin/owner role concept yet to check against for real, so that's the honest, narrowest fix rather than inventing a permissions model on the spot.
- **A JWT session's `sub` is only ever validated cryptographically, never against the database — a browser can hold a perfectly "valid" session pointing at a `User` row that no longer exists.** Hit this for real right after landing real auth: `POST /api/workspaces` connects the caller as a member via `members: { connect: { id: userId } } }`, and when that id didn't correspond to any actual row, Prisma threw a raw `P2025` ("Expected 1 records to be connected, found only 0") that crashed the route with a 500 and an empty body — which the client then failed to `.json()`, surfacing as a confusing `SyntaxError: Unexpected end of JSON input` with no obvious link back to the real cause. `getCurrentUserId()` (`lib/auth/session.ts`) now does one extra `findUnique` to confirm the id is real before handing it back, treating a stale/orphaned session exactly like "not signed in" (empty results from GETs, 401 from mutating routes) instead of crashing. Worth remembering for *any* JWT-session app with a relational DB behind it — a dev DB reset/reseed, or any direct row deletion, can silently orphan a still-"valid" cookie in someone's browser.
- **Filtering a tree by per-row visibility isn't enough when the tree is returned as flat sibling arrays instead of actually nested — a child can leak through even though its parent didn't.** Building per-level private access, `GET /api/workspaces` filtered each Folder and List by its *own* `isPrivate`/`accessJson` only — but Prisma returns `space.folders`/`space.lists` as flat arrays (linked by `folderId`, not physically nested), so a List sitting inside a private, inaccessible Folder — while not itself private — still came back, since nothing ever checked its parent chain. Folders nest arbitrarily deep, so "check one level up" wouldn't have been a complete fix either. `buildFolderChainVisibility()` (`lib/auth/access.ts`) loads a scope's full, unfiltered Folder set once and walks `parentId` chains in memory instead. Caught by the plan's own verification checklist (a 4th test user expected to see only an open List, but saw the hidden one too) rather than assumed correct — worth remembering that "filter by isPrivate" and "filter by is-actually-reachable-from-the-root" are different checks whenever a hierarchy is flattened before being sent to the client.
- **`next dev`'s route handlers hand Auth.js (and presumably any other code reading `req.url`) a request whose URL stays pinned to the dev server's own "Local" origin, regardless of which Host header a request actually arrives with.** Confirmed directly with `curl` against the real LAN IP, zero header spoofing. `trustHost` doesn't touch this — it only gates whether an unrecognized host is *allowed*, never what origin request-URL-derived logic uses. The only override is setting `AUTH_URL` explicitly. This is a `next dev`-only limitation (worth re-verifying, not assuming, once actually deployed behind `next start`).
- **A plain `tsx`-run script (unlike `next dev`) loads no environment variables automatically** — this project's SQLite datasource URL is hardcoded in `schema.prisma`, so `server/collabServer.ts` never needed any env var and the gap went unnoticed for months. Node 24's native `--env-file=.env.local` flag (prepended in the relevant npm script) is the fix — confirmed `tsx` forwards it straight to Node, no new dependency needed.
- **Hocuspocus's `onAuthenticate` hook fires unconditionally on every new document connection** (not gated behind the client explicitly passing a `token`) **and receives the raw WebSocket-upgrade request headers**, including `Cookie` — meaning a Hocuspocus sidecar can reuse a web app's own session cookie for auth with zero client-side changes, rather than needing a separate token-minting endpoint. Worth remembering as the default approach for authenticating *any* future non-Next sidecar/service that shares an origin (cookies aren't port-scoped) with this app.
- **When verifying a security fix, drive the real client library/protocol against the real running server, not a hand-rolled approximation.** Verifying the Hocuspocus auth fix used the actual `HocuspocusProvider` client (via a Node `WebSocketPolyfill`, `ws`, temporarily installed with `--no-save`) against the real sidecar, rather than trying to fake the Yjs binary wire protocol by hand — the latter would have been both harder to get right and less trustworthy as proof the *real* client/server pairing actually rejects unauthorized connections.
- **A dev server has only ever been reached via `localhost` until someone actually tries a second machine on the LAN — and two independent things break the moment that happens, not just one.** Next's dev server silently blocks cross-origin requests to dev-only resources (the HMR websocket) by default, which can leave a page half-hydrated in a way that looks exactly like "nothing responds to clicks," not like a console error pointing at the real cause. Separately, without an `AUTH_URL`/`NEXTAUTH_URL` env var, Auth.js's own auto-redirect to the sign-in page inferred `localhost:3000` instead of the request's actual origin — meaning a successful login on the second machine would've bounced its browser to *its own* loopback address. `trustHost: true` (`auth.ts`) fixed Auth.js's internal OAuth-state cookie immediately (verified via a raw `curl -H "Host: ..."` request) but *not* the `/login` redirect's own `callbackUrl` query param, which came back wrong through what's apparently a different code path — worth remembering that "trust the host" isn't necessarily one single on/off switch inside a library, and confirming the *specific* value that was wrong (not just that the feature now works in one place) is what caught the gap. Fixed at the point of use instead — `app/login/page.tsx` now strips any `protocol://host` prefix off `callbackUrl` before using it, since a same-app redirect should never legitimately need to leave the current origin regardless of what built the URL. Google sign-in specifically also needs the new origin added as an Authorized redirect URI in Google Cloud Console — that one has no code-level fix, since Google itself validates the exact registered URI.
- **A cross-render "stability" hint (keep this in the same lane/slot it had last render, to avoid visual jitter) can directly conflict with a packing algorithm's correctness guarantee.** `assignLanes`' `previousLanes` hint was added purely to stop a dragged task from reshuffling every other task's lane on the same render — but once a cluster's membership shrank, neighbors' stale hints kept pointing at their own old, now-non-adjacent slots instead of recompacting, leaving a visible gap and an inflated overflow count. When a user explicitly asks for tight/minimal packing, don't try to patch a stability hint to also be correct — just drop it and recompute fresh every render; a classic greedy algorithm (first-fit-by-start-time, here) is often already stable-*enough* in practice without one.
- **A shared/global layout value silently couples unrelated rows or cells together — and a partial per-row fix can leave a second global value behind that looks unrelated but has the same shape of bug.** The Planner overflow-count bug was root-caused twice in one session: first the lane-assignment itself (`assignLanes` called once per month instead of once per row), then — after the user caught it via a follow-up screenshot — the row height and the chip's vertical offset were *also* still each computed once from the whole month's data and shared across every row. Any time a "seems fine now" layout constant is touched during a per-row/per-item fix, grep for other reads of the same broader-scoped value before declaring the bug closed.
- **Verify visual/CSS claims by measuring (`getComputedStyle`, `getBoundingClientRect()`), not by eyeballing a screenshot.** Two real instances same session: `rounded` and `rounded-sm` compute to the identical 4px in this project's Tailwind v4 setup, so a first "make it sharper" attempt was a silent no-op until measured directly (`rounded-xs`, 2px, was the actual fix); separately, a chip's reserved height constant (`OVERFLOW_H = 14`) had quietly drifted from the chip's real rendered height (measured 24px), causing a few px of overflow past its cell's bottom edge that wasn't obvious from a screenshot alone but showed up immediately as a negative `distanceToCellBottom` once actually measured.
